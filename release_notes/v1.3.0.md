# PrWaiter 1.3.0

**取数按优先级分档 —— `gh: HTTP 504` 的真解。**

1.2.1 那次把大查询拆成小块，只是把每条压到超时线以下，**总量没变**，PR 再攒一批还会撞上。

## 为什么

贵的是 check 明细：每个 PR 要展开 100 条 check context + 50 个 check suite。而
**只有还开着的 PR 用得上它** —— 已合并 / 已关闭的本来就不算 CI，那一栏根本不显示。

实测一台机器上跟踪着 86 个 PR，其中**只有 4 个是 open 的**。也就是说 95% 的 check 明细
拉回来直接丢掉，纯粹白花服务端开销。

## 现在怎么拉

- **还开着的** —— 每次刷新都拉全字段（含 check 明细）
- **已合并 / 已关闭的** —— 只拉基本字段，而且每次只顺带带 5 个、轮着来。
  已合并是终态；已关闭偶尔会被重开，所以不必每次查，但也不会永远不查
- **还没拉过的** —— 先只拉基本字段（那时还不知道谁是 open），拿到状态后再给
  「其实是 open 却还没 check 明细」的那几个补一次小查询

实测：

```
旧：一条大查询全字段        0/6 成功，平均 14.3 秒
新：3 全字段 + 5 基本        8/8 成功，平均  3.9 秒
新：三个项目并发跑 6 轮      5/6 干净，平均  5.4 秒
```

## 每行多了个刷新按钮

低优先级的 PR 平时是轮着捎带的，想立刻看某一个的最新状态，点它那行的刷新按钮单独拉全字段。

## 还修了

**某条查询失败时不再显示「拉取不到，检查编号或仓库设置」。** 保留上一轮的值 ——
陈旧但真实的状态比那句话有用得多，后者看着像编号填错了会把人带偏。界面上用一条
琥珀色提示说明「有 N 个 PR 这次没拉到，显示的是上次的状态」。

GraphQL 重试从 1 次提到 2 次（共 3 次尝试，退避 1s / 3s）。

## 升级

设置 → 更新 → 「检查更新」→「下载并安装」。
