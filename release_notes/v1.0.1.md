# PrWaiter 1.0.1

**修一个会误导人的 bug：CI 明明没跑完，界面显示「CI ✓」。**

## 问题出在哪

GitHub 的 PR 页面会写「Some checks haven't completed yet — 23 skipped, 8 expected,
19 successful checks」，其中那几项 **Expected — Waiting for status to be reported**，
指的是分支保护里配了必过、但这个 commit 上一次都没出现过的 check。

坑在于：**它们不在任何 check 接口里** —— 不是 check run、不是 check suite、也不是
status context，连 `gh pr checks` 都看不见（只会说 19 pass / 23 skipping）。
不查它们，就会把「重活还没轮到跑」显示成「CI 通过」。

## 改了什么

**多查一次分支保护的必过项清单**（`repos/{repo}/branches/{分支}` 的
`protection.required_status_checks.contexts`，只要读权限就能读），跟已报上来的比对，
缺哪怕一项就算「运行中」。实测某个 PR：要求 14 项、报上来 34 个 check、缺 8 项，
跟界面上那个数字一致。

**不再直接信 `statusCheckRollup.state`。** 那个字段算不准，而且取决于你怎么问 ——
同一个 commit、同一时刻：

```
statusCheckRollup { state }                     ->  SUCCESS
statusCheckRollup { state contexts(first:100) } ->  FAILURE
```

因为它把同名 check 的历次尝试都算进去了：某项挂了、重跑成功，旧那条 FAILURE
还挂在 commit 上。现在自己按明细算，同名只取最新一次尝试。

**只认 IN_PROGRESS 的 check suite，不认 QUEUED。** 仓库上装的每个 GitHub App 都会给
每个 commit 挂一个 suite，多数一条 check run 都不发，永远停在 QUEUED。认 QUEUED 的话，
早就合并的 PR 会永远显示「CI 运行中」。

## 顺带

**check 明细只给还开着的 PR 拉。** 刷新分两趟，第一趟只要基本字段。已合并 / 已关闭的
PR 追究 CI 早就没意义了，跳过第二趟能省很多 —— 实测一个 20 个 PR 全是已合并/关闭的项目，
刷新只要 2 秒、6 KB（拉全量明细要 15 秒、190 KB）。

所以**已合并 / 已关闭的行不再显示 CI 徽标**。那本来也是噪音，旧尝试留下的假红经常挂在上面。

## 升级

设置 → 更新 → 「检查更新」，点「下载并安装」即可，App 会自己替换并重启。
也可以直接下 DMG 拖进 Applications 覆盖。
