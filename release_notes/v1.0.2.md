# PrWaiter 1.0.2

**刷新快了：一次刷新只发一个请求，不再发四个。**

## 为什么是「请求个数」而不是「数据量」

量了一下时间花在哪，结论有点反直觉。这条网络到 `api.github.com`：
**TCP 连接只要 2ms，TLS 握手却要 1–5 秒**。而 `gh` 每调用一次就是一个新进程、
一条新连接、一次新握手。

| 测什么 | 耗时 |
| --- | --- |
| 同一个查询，**1 个** PR 别名 | 5.1 s |
| 同一个查询，**20 个** PR 别名 | 6.6 s |
| 3 个请求，各自新建连接 | 14.6 s |
| 3 个请求，**复用同一条连接** | 7.2 s |

数据量几乎不要钱，**每多一次往返就多 5 秒**。

## 改了什么

原来一次刷新发四个请求：两次 `gh pr list`（作者 / 指派）+ 一趟 GraphQL 拉状态
+ 一趟拉 CI 明细。现在全挤进**一条** GraphQL —— PR 状态、CI 明细、以及
「作者是我」「指派给我」两个搜索，一次拿回。`gh pr list` 那条路整个删掉了。

1.0.1 里那个「check 明细只给 open PR 拉」的拆分，方向正好反了：
拿「+2 秒的数据量」换了「+5 秒的往返」。这版合回一次请求，明细照拉，
但仍然只对 open PR 计算 CI 结论（已合并 / 已关闭的那一栏不显示，那是噪音）。

同一时段头对头：**11.7 秒 → 9.4 秒**。而 11.7 秒还是旧流程的最好情况 ——
那个项目里一个 open PR 都没有、第二趟被整个跳过；有 open PR 时旧流程是 ~17 秒。

一个代价：**新导入的 PR 要等下一拍刷新才有标题和状态**。搜索结果和状态是同一次
请求带回来的，拿到搜索结果时状态那部分已经发出去了 —— 为这个再跑一次往返不值。

## 还剩下的地板

单次请求 ~9 秒里有 ~5 秒是 TLS 握手，这是这条网络的地板。TLS 会话恢复试过，没用
（完整握手 5.3–5.8 秒、会话恢复 5.0–5.3 秒），说明不是加解密开销，而是按 SNI 的定向延迟。

再往下只能靠保持一条连接不断开（热连接上后续请求只要 ~1.1 秒），那需要应用自己维持
HTTP 连接而不是每次 fork 一个 `gh`。暂时没做。
