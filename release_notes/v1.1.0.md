# PrWaiter 1.1.0

**多了一个 reviewer 视角。** 此前整个 App 都是创作者视角 —— 我写的 PR 排到哪了、该催哪个；
这一版补上另一半：**别人卡在我这里的事**。

动机很实际：GitHub 的邮件多到根本看不完，别人的流程卡在你这里，往往就是因为那封邮件被埋了。

## 怎么用

刷新和设置中间多了一个**「切换到评审视角」**按钮，右上角带待办数气泡（有「等我批准」时变橙）。
切过去是一份「谁在等我」的清单，按**卡得多死**排序：

1. **等我批准** —— workflow / 部署卡着等我点批准。不批就永远不跑，作者在那边干等
2. **请我 review** —— 指名或按团队请我看的
3. **指派给我** —— 别人建的 PR 把我设成了负责人
4. **@ 到我** —— 有人在 PR 里点了我，等我回话

每行显示：仓库、编号、标题、目标分支、在等我的那个人、CI 状态，以及**别人等了我多久**。
标签上带未处理数量，有「等我批准」时变橙色。

这一页刻意跟看板长得不一样：**没有树、没有拖拽、不能编辑**。别人的 PR 我管不着合并顺序，
只需要一份从上往下办完的清单。它也不按项目分 —— 是跨全部已配置仓库的一份总清单。

**两个视角是两套东西，互不串门。** 看板已经在跟的 PR，评审清单里不会再出现一次。

**一次刷新把所有项目和两个视角全刷了**，不再只刷当前那个 —— 否则切过去总要再等一次，
而且切换按钮上那个待办数会一直是旧的。各项目并发拉，总耗时约等于最慢的那一个。

## 几条刻意的取舍

**只列别人的 PR。** 搜索里带 `-author:@me` —— 我自己的 PR 归看板那边管，混进来只是噪音。
同理，我已经 review 完批准了的也不列：球在作者那边，我不是瓶颈了。

**「等我批准」单独查，不能只看 review 清单。** 随便一个贡献者的 fork PR 卡着等我批，
没人会请我 review，搜索里根本看不到它。两种形态都认：环境审批（靠
`pending_deployments` 的 `current_user_can_approve` 确定是不是等**我**，不是等别人），
以及 fork 首次贡献者那种。

**只查我有写权限的仓库。** 批 workflow 要写权限，只读的仓库连查都不用查 ——
省一次请求（这条网络上一次请求要 5 秒）。

**「别人从什么时候开始等我」取自 timeline**，不是 PR 的更新时间。三天前请我 review、
刚被作者推了一版，不该排到「十分钟前请我」前面。

**「@ 到我」会自己消掉。** 另两档 GitHub 自己会撤（提交 review 后请求自动撤销、批准后 run 就走了），
只有 @ 是历史事实，PR 开着就永远匹配，不管的话会越堆越多、变成你想躲开的那种噪音。规则是：

> **有人在我最后一次发言之后又点了我**，才算还欠着。

所以**不必回复那条 @ 本身** —— 提交 review（含批准）、新加评论、回复他，任何一种都算我接手了。
我说完之后别人再点我一次，它会带着新时间戳重新冒出来。

还有个**「忽略本次」**按钮，兜住那种「知会一声、不用我回」的 @：点一下消掉，
按这一次被点的时间记账，下次再被 @ 还会出现 —— 不是永久屏蔽这个 PR。

**别人先把 PR 合掉之后，「等我批准」也会消失。** 另三档搜索里带 `is:open`，PR 一合上自动就不在了；
但批准项是从 workflow run 来的，PR 合了那个 run 还挂在 waiting 上。流程都走完了，不该还堵在我这。

**仓库名显示 GitHub 返回的真名。** 仓库改名 / 转移之后用旧名照样查得到（GitHub 会重定向），
但显示旧名会让人对不上号。
